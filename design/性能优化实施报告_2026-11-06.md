## 2. 各任务实现要点（与方案契约对照）

### T00
- `Perf`/`PerfRecorder`：阶段计时聚合（环形 2048 采样/阶段，p50/p95/max 按需计算）、计数器、最慢 32 段留存；阶段常量齐全（§4 列表）；跨线程 requestId 关联。埋点已接：`app.inject`（MyApplication super.onCreate 段）、`db.open`（DbRuntime 开库）、`reco.cache.read/render/flush`、`diff.compute/apply`、`cover.load`、`hls.phase.*`。
- `ExecutorRegistry`：dbWrite/stateWriter/diff(≤2)/parseForeground(1)/parseBackground(2)/warm(1)，30s 空闲回收，线程可命名定位。
- `PerfFlags`：§4 全部九个开关。
- `VideoKey(source, canonicalViewKey)`：集中 viewKey 归一化（幂等，兼容 `viewkey=` 前缀型与路径型），JVM 单测 7 例。
- benchmark buildType：`initWith release`（R8/资源收缩保留）、`profileable`、包名后缀 `.perf`（测试数据隔离，不触碰正式包）、`PERF_STRICT=true`（StrictMode 仅测试/调试构建启用）。
- 脚本：`build-tools/perf/perf_run.py`（--serial/--apk/--scenario/--iterations/--output；缺设备明确失败 exit 2；cold_start 用 force-stop 保数据；输出 environment.json + summary.json，schemaVersion=1，NOT_RUN 不标 PASS）、`perf_compare.py`（PASS/FAIL/NOT_RUN + 同 APK 比较无效检测）、`seed_db.py`（instrumentation 注入，0/1k/10k/50k 行）。
- 测试：JVM 单测（VideoKeyTest 7 例、PerfAggregationTest 5 例、ExecutorRegistryTest 3 例——锁池并发上限/串行性）；设备冒烟 `PerfSmokeTest`（聚合真机可用性 + 执行器派发）。

### T01
- `RecoBatchCache.read/writeLatest`：JSON 编解码全在缓存执行器（PARSE_BACKGROUND）；scope=格式版本+源配置摘要(SHA-256 前 16 hex)+方向筛选+时长上限，不匹配视为未命中；≤256KB；24h 旧批不展示不自动起播；坏 JSON 按未命中；writeLatest 合并旧写+尾沿补写（drainBusy CAS + finally 补投）。
- Fragment：onViewCreated 即并行启动缓存读取与引擎初始化；状态机 EMPTY_LOADING→CACHE_VISIBLE→NETWORK_VISIBLE/EMPTY_ERROR；已有条目不再盖 globalLoading；引擎 ready 后缓存已上屏走 `loadMore(false)` 静默续拉；pendingAutoPlay 只消费一次（不重复起播/曝光）。
- 去重：缓存与网络按 `VideoKey` 去重；网络同 key 就地回填 detached 壳标量（不 notifyItemChanged，不重启播放器）；批内重复也去重；全部重复=成功空操作（不进空批重试）。
- 兼容：flag 关闭走原 v1 `showCachedBatchFirst` 路径逐行保留；预取开关语义不变（关=不读缓存）。

### T02
- `AsyncAdapterDiffer`：主线程捕获快照 → DIFF 池（≤2）calculateDiff → 主线程代际校验 → 原子切换 + dispatch；A 慢 B 快只显示 B；pendingTarget 只留最新（不无限排队）；计算期间外部改动（追加/清空）重捕获一轮（≤3 轮退回 setNewData）；空↔非空走 setNewData 保 BRVAH 空视图；派发语义与 M115 一致（header 偏移行为不变）。
- `AdapterDiffUtil.apply` 签名不变，10 个调用点（历史/收藏/作者/下载完成/评论）零改动获得异步能力。
- 身份修复（E03）：V9MmanItem 身份 viewKey 优先（网络项 id=null 可稳定识别），DB id 回退，两者皆空不共享 NO_ID。
- 备注：方案中的完整不可变 Row（VideoRow/AuthorRow/CommentRow）迁移未做——当前为"主线程快照 + 代际校验"等价隔离，实体字段并发变化由刷新轮兜底；Row 化与 T08 UI 迁移一起做更省（见 §4 风险）。

### T03
- E04 根因修复：展示 `load(Uri)` vs 预取 `load(String)` model 类型不一致 → 缓存键永不命中。现统一 String model + override + SmartCoverTransformation。
- `CoverRequests.Spec`（不可变）：实测尺寸优先（与旧 override(w,h) 行为一致）；未布局回退注册尺寸（推荐页 initViews 注册全屏实测，`registerCardSize`）；横竖屏/尺寸变化天然生成新 spec；预取禁 SIZE_ORIGINAL（未定尺寸不预取）。
- tag 改存完整 Spec；失败清 tag 允许重试；onViewRecycled 走 `clearBoundSpec`；异步方向回调校验当前绑定 url（防复用错位）。
- 方向表改 LRU ≤800（不再整体清空——旧 clear() 会让滑动中角标集体退化）；resource disk hit 不重跑 transform → 方向未知保持未知语义；模糊缩略图从 BitmapPool 取还（try/finally），不 recycle source。

### T04
- `updateWindow(list, currentPos, ahead)`：窗口=当前+后续 ahead；出窗后台解析真取消（dispose，且有等待者保护）；后台在途 ≤8；同 key 单飞（inFlight）。
- 前台/下载等待（resolveNow→urgent parse）不在可取消表，翻页不误伤；`cancelBackground()` 于 onHiddenChanged(true)/release 调用；release 断开 warm 连接。
- 分级负缓存：断网/超时/5xx 5s；解析无结果 10min；403 一次快速重解析（1s）后转长封禁；LRU ≤120 + 过期清理；`bypassNegativeCacheOnce` 供显式重试。
- warm：1 执行 + 1 待队（warmPending≥2 跳过）；HLS manifest warm 第一期禁止；MP4 每次 read `min(buf, remaining)`，512KiB 上限，Range 被忽略时如实记录实际读取量。
- 预取开关关闭：updateWindow/prefetch 均短路；播放/下载解析不受影响。

### T05
- `HlsDownloader`：协调线程（解析/合并/转封装/清理）+ 3 个长活 worker 从 AtomicInteger 领片（10,000 片无 Runnable 线性积压，在途 ≤3）；latch 只等 3 个 worker（finally countDown）。
- `.part`→rename 纪律：续传非空正式片可信；`started.json` 分片 URL 集合摘要，不匹配保守清旧片（防签名变化/同名目录碰撞误复用）；活动连接注册表，stop 立即 disconnect（1 秒内停止新增读取）；stop(true) 清理由协调线程在 worker 退出后执行（不边写边删）；合并前空间预估（片段+merged+mp4 ×1.1），不足清晰失败且保留可续传片。
- `HlsDownloadService`：节流前置——通知/广播各 500ms、DB 2s（按 rowId 定向更新进度列，不 findItem 不整行覆盖，收藏/来源不被过时快照回写）；内存采样随事件更新；进度单调（乱序旧值丢弃）；终态单次提交（AtomicBoolean，START 复位）；阶段回调 onPhase 立即 flush（merging/remuxing/archive 单列计数）；被替换旧任务置 PAUSED 逻辑保持。

### T06
- `RecoPersistenceCoordinator`（进程级单例，持 appContext）：requestSave(reason, urgent) 普通 2s 合并/urgent ≤500ms；更早调度可覆盖合并请求（执行时取最新快照→无旧版本后写、无丢请求）；写失败退避重试 1/2/4s×3，之后等下次触发；`flushForTest()`。
- `RecoStore`：saveNow(reason) 返回真实结果；mkdir 移出状态锁（ioLock 内）；AtomicFile startWrite/finishWrite/failWrite 替代"先 delete 后 rename"（写失败 failWrite 恢复上次有效文件、不删原文件）；ensureLoaded 走 openRead（base/backup 自动兼容，旧 JSON v2 可读）；清脏仍核对 dirtySeq。
- Fragment：persistAsync/onDestroyView 只发请求，不再把保存订阅塞进 CompositeDisposable（销毁 clear 不再取消保存，尾沿不丢）。
- 备注：方案中的 epoch 机制未引入——单写者串行 + 执行时快照使"旧 epoch 任务恢复旧数据"在本模型下不成立（无排队快照）；如后续引入排队快照需补 epoch。
- 画像复合修改 mutateState/RuntimeConfig 不可变发布：RecoEngine.updateParams 已是"局部构建后整体替换"模式，本次未改动（无两 volatile 组合竞态的实锤路径）；打分线程画像快照维持现状。

- AppDbHelper：40 处 mDaoSession → daoSession()；种子+误标修复仍在后台线程 ready 后串行（顺序与旧版一致）。
- 进程 gate/通知渠道/代理 Cookie 初始化顺序未动；仅 T00 确认超预算的初始化才延后——db.open 段已有埋点，等基线数据决策。
- **同步入口审查结论（第二轮）**：
  - Search/Mine：DB 访问已走 IO 调度（RxSchedulersHelper / Schedulers.io），合规；
  - DownloadPresenter.startDownload 595 行主线程写库 → **已改 IO fire-and-forget**（写结果不被调用方使用，无读取竞态）；

## 7. 剩余风险与回退

1. **T01 同 key 元数据回填**改 detached 壳标量：若候选实体来自 greenDAO session（insert 后 attach），原地改字段不落库、但会反映在 session 身份缓存——语义与"网络权威元数据"一致，风险低；验收场景（反复进出/旋转）需设备验证。
2. **T02 快照隔离**非完全 Row 化：极端并发改字段可能产生一次陈旧 diff，由刷新轮自愈；关闭 asyncDiff 即回退同步路径。
