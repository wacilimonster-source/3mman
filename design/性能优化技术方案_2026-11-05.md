# 3mman 性能优化技术方案（可交付 Agent 实施）

日期：2026-11-05  
审查基线：工作区 `G:/game/nw/3mman`，HEAD `d1453dc`，App `1.0.128 / versionCode 161`。  
交付性质：源码审查与实施设计；本次不修改业务代码、不构建或发布 APK。下文所有耗时、内存收益均为验收目标，不是已测结果。

## 1. 结论与实施范围

优先优化四条链路：**启动与推荐首屏、滑动与封面、预取与起播、HLS 下载与进度更新**。其次治理大数据列表、推荐状态持久化和长会话内存。

第一阶段保留 Java 8、MVP、RxJava 2、greenDAO、Glide、JiaoZi 播放器体系，避免把架构迁移混入性能修复。推荐页实际使用 `RecoVideoPlayer extends JZVideoPlayerStandard`；`exolibrary/ExoVideoView` 属另一播放链路，不应误认为推荐页改它即可生效。

技术基线：AGP 7.4.2、Gradle 7.6.4、JDK 17、minSdk 28、compile/targetSdk 34、arm64。新增工具依赖必须兼容此组合；不能直接套用最新 Android 示例要求整体升级工具链。

本方案不改变推荐排序公式、内容源、筛选语义、自动连播、收藏、观看历史和下载归档语义。源码注明预取不区分 Wi-Fi/移动网络，这是既有用户选择，不能借优化擅自改为仅 Wi-Fi。也不强制缓存登录页、详情页或签名播放 URL。

## 3. 性能目标、测量口径与环境

### 3.1 固定测量条件

T00 首先生成 `reports/performance/<run-id>/environment.json`，记录 commit、工作区差异摘要、APK SHA256、设备型号/RAM/API、刷新率、包版本、编译模式、网络模型、缓存状态、数据规模及温度。APK 与源码必须一一对应，不能拿现存根目录 APK 当作当前工作区构建结果。

至少两台 arm64 真机：4GB 内存的 API 28~30 设备，以及 API 34+ 设备。模拟器用于功能自动化，不作为最终性能门禁。比较时固定刷新率 60Hz、前台亮度、供电状态和编译模式；热降频批次作废重跑。另补一次高刷新率功能检查。

测试构建：新增仅用于测试的 benchmark buildType，从 release 继承，保持 R8/资源收缩，设 profileable；禁止把 debug BODY 日志开启后测得的耗时作为 release 基线。独立 benchmark 模块建议以 AndroidX Benchmark 1.2.4 为候选，先验证现有工具链可构建，成功后锁定依赖；若不兼容，T00 先交付 adb + Perfetto 测量，不升级主工程解除阻塞。编译模式统一使用可重复的无预编译基线，之后再单独比较 profile 收益。

测试数据：自有/获准使用的本地 HTML、封面、MP4、HLS 固定样本；不要依赖第三方站点当天速度。准备正常网络（10Mbps/RTT50ms）、弱网（1Mbps/RTT200ms）、离线、403过期、慢响应、忽略 Range 等模型。分别记录代理开/关。通过测试专用数据源注入接入样本，不在正式包新增公网调试入口。

数据规模：数据库 0 / 1,000 / 10,000 / 50,000 行；推荐连续翻 1,000 次；HLS 10 / 1,000 / 10,000 片及 >2GB 文件。种子只写专用测试包/测试数据库，不清空用户数据。

### 3.2 指标定义与建议门槛

先跑未优化基线，再用同一脚本比较。时延样本不少于 50 次，输出 p50/p95 与原始记录；内存长跑至少 3 次。不要只报平均数或把失败请求剔除后宣称变快。

| 指标 | 起止事件 | 初始验收目标 |
|---|---|---|
| 冷启动 TTID | 系统启动 Activity → 首帧 | p95 相对基线降低 ≥15%；基线已很快时以不退化 >5% 验收并记录理由 |
| 推荐缓存首屏 | 点击推荐 Tab → 已提交布局、首个有效封面可见且手势可用 | 有缓存 p95 ≤500ms；与引擎/网络完成解耦 |
| 推荐起播 | 选中页 → 首个视频画面 | 本地固定样本、有效直链且媒体预热命中时 p95 ≤800ms；未命中另统计，不能混算 |
| 滑动流畅度 | 60Hz 固定脚本、帧时长 | >16.67ms 帧比例 ≤5%，无本次应用任务造成的 >700ms 冻结帧；同时保存 FrameTimingMetric/Perfetto |
| 主线程工作 | 推荐进出、列表刷新、下载开始/暂停 | 自有 DB/文件/JSON 全量处理不在主线程；主线程本次更新段 p95 ≤4ms（小批 UI 提交） |
| HLS 资源 | 10,000片运行与取消 | 分片在途 ≤3、待执行分片任务 ≤6；普通通知/广播各 ≤2次/秒，DB进度写 ≤1次/2秒，终态例外 |
| 列表查询 | 50,000 行、首批50及深分页 | 本地 DB 查询 p95 ≤50ms；UI 不全量装载收藏/完成记录 |
| 长会话内存 | 1000次翻页、固定样本、稳定后测 Java heap/PSS | 预热后每100次相同操作的稳定采样不持续单调增长；T09完成后内存驻留条目≤200、辅助表≤500，100→1000页 Java heap增长≤20MB |
| 稳定性 | 全部回归 | 无新增崩溃/ANR；收藏/下载/历史不丢失、无旧任务覆盖新任务 |

绝对目标在 T00 低端设备结果后可修订一次，写明理由与最终门槛；禁止到验收时再为失败下调。线上真实源时延仅作补充，分别记录排队、DNS/连接、TTFB、解析、准备和首帧，网络站点耗时不能算成客户端优化收益。

TTID 与可用内容/TTFD 是不同指标，Application.onCreate 耗时也不能替代二者。按 [Android 启动测量定义](https://developer.android.com/topic/performance/issues/launch-time) 设置 reportFullyDrawn：内容已可用或明确的空/失败页可交互后调用一次；视频首帧独立埋点。

## 4. 公共约定：执行器、身份、异步与开关

新增 `J/perf/`，提供以下基础件，T00 负责建立契约，业务任务按需使用：

```java
interface PerfRecorder {
    long begin(String stage, long requestId);
    void end(String stage, long requestId, long beginNs, String outcome);
    void counter(String name, long value);
}
// ExecutorRegistry：进程级，使用 applicationContext，不持有 Activity。
// dbWrite: 单线程；stateWriter: 单线程调度；diff: 最多2线程；
// parseForeground: 1并发；parseBackground: 2并发；warm: 1并发。
// 不强行把现有全部 Rx 链迁入一个线程池；各任务只接管其声明范围。
```

埋点阶段：`app.inject`、`db.open`、`reco.engine.init`、`reco.cache.read`、`reco.cache.render`、`reco.batch`、`parse.queue/db/network/html`、`player.prepare/first_frame`、`cover.load/transform`、`diff.compute/apply`、`hls.segment/merge/remux/archive`、`reco.flush`。跨线程用 requestId 关联单独区段，不跨线程配对同步 Trace.begin/end。采样聚合后本地记录，不每帧写日志，不自动上传，不记录完整签名 URL、Cookie 或用户标题。

身份使用不可变 `VideoKey(source, canonicalViewKey)`；集中封装现有前缀/裸 key 归一化规则，不擅自改库里的 viewKey。UI/请求 token 使用 `generation + key`，下载再加 `taskId`。取消是尽力而为，**所有迟到结果还必须校验 token**。

新增内部 `PerfFlags`：cacheFirst、asyncDiff、coverRequestV2、prefetchScheduler、hlsScheduler、stateWriter、lazyDb、pagedLocalList、feedWindow。默认开发分支逐项打开，正式开关由发布配置决定，不增加产品设置项。开关关闭时保留可读的数据兼容性；正确性修复（终态保护、原子写盘）不允许退回不安全路径。

## 5. 任务实施规格

### T00 / P0：建立基线与性能回归工具

**改动**：`J/perf/*`、测试专用源工厂、`app/src/androidTest/.../perf/`、`build-tools/perf/`；benchmark 模块兼容性验证成功后才修改 settings.gradle。生产仅保留低开销计数与阶段计时。

**实施**：

1. 建立固定样本、MockWebServer（与实际 OkHttp 依赖版本对齐）、设备脚本和数据库种子生成器。测试接口从测试代码注入，不能通过线上 Intent 任意替换源。
2. 脚本支持 `--serial --apk --scenario --iterations --output`，包安装为显式测试步骤；缺设备则明确失败，不生成成功报告。冷启动使用 force-stop 保留用户数据；不要 pm clear 模拟冷启动。
3. 加 StrictMode 调试策略检测磁盘/网络主线程访问，只在测试/调试启用；采集 adb gfxinfo、meminfo、Perfetto 和 benchmark JSON。StrictMode 不能替代调用链检查。
4. `summary.json` 使用 schemaVersion，保存 sampleCount/failureCount/p50/p95/cacheHit/queueDepth/bytes；比较器输出各指标 PASS/FAIL/NOT_RUN，未执行不得 PASS。

**验收**：同一 APK 连跑两轮结果差异可解释；能单独识别网络慢、解析排队和播放器准备慢；提交基线报告和最慢10段 trace。其余任务可先编码，任何性能收益结论须依赖基线。

### T01 / P0：推荐缓存首屏脱离引擎关键路径

**改动**：RecommendFeedFragment；新增 `ui/recommend/RecoBatchCache.java` 与轻量不可变 `CachedVideo` DTO。

**接口**：`Single<CacheBatch> read(CacheScope scope)`；`void writeLatest(CacheScope scope, List<CachedVideo> items)`。scope 包含源配置摘要、方向/时长筛选、格式版本；不写签名直链、DaoSession 或整个 greenDAO 对象图。最多 BATCH_SIZE 条、编码后≤256KB，记录时间，超过24小时不自动起播旧批。

**顺序**：

1. onViewCreated 完成 View 后并行启动缓存 IO 和现有引擎 IO。Adapter 引擎暂空时互动禁用或排队，不能偷偷在 bind 中调用 RecoEngine.get 同步初始化。
2. 缓存 IO 解析/过滤/构造 DTO；主线程只接收不可变批次并渲染。引擎 ready 后回填互动状态、启动网络召回；只在引擎 ready 且当前页仍有效时执行需要画像的自动起播/曝光结算。
3. 明确状态 `EMPTY_LOADING / CACHE_VISIBLE / NETWORK_VISIBLE / EMPTY_ERROR`；已有条目时不能重新显示遮挡整个内容的 globalLoading。缓存命中和网络谁先返回，后到结果不能清空前到内容。
4. 缓存与网络按 VideoKey 去重；网络同 key 更新权威元数据，保留正在播放 ViewHolder 与位置，不重启播放器。generation 随筛选/刷新/视图重建递增，丢弃旧缓存结果。
5. JSON encode/read/write 都在缓存执行器；主线程先复制必要标量字段，不能把活的实体传给后台 Gson。writeLatest 合并尚未执行的旧写，只写最新批。

**验收**：缓存坏 JSON、离线、筛选变化、源变化、引擎慢2秒、网络先到、反复进出各测；缓存首屏不等2秒，不重复自动播放/记录曝光，不展示不符合当前筛选的旧内容。未开启预取时保持现有缓存启用规则，不借此改变设置语义。

### T02 / P0：异步 Diff 与不可变列表快照

**改动**：AdapterDiffUtil 及 E03 所列全部调用点；新增 `AsyncAdapterDiffer`、`VideoRow/AuthorRow/CommentRow` 或等价不可变渲染快照。

**接口**：每个 adapter 独立 `submit(List<Row>, generation)`、`append(List<Row>)`、`dispose()`。计算线程最多保留正在计算的任务与一个最新目标，不为每次刷新无限排队。可参考 AsyncListDiffer 思路，但保留 BRVAH 2.x header、empty、loadMore 行行为。

**算法**：在主线程捕获已提交的旧不可变列表和新不可变列表；后台 calculateDiff；回主线程校验 submitGeneration 与 adapter 生命周期；原子切换列表后 dispatch。过期结果丢弃。append/删除/刷新统一经过该入口，禁止一边 diff 一边直接改 adapter.getData()。映射成本大时在 DB 查询线程生成 Row，禁止浅复制 greenDAO 实体后认为隔离完成。

`areItemsTheSame` 优先 VideoKey；缺业务 key 的纯本地记录回退 id，未知对象不能都返回同一个 NO_ID。contentEquals 必须覆盖真实绑定字段（含来源/作者/方向/收藏），进度使用 payload，不能重绑封面。header offset 在 dispatch 层统一处理并测试。

**验收**：A慢/B快两次提交最终只显示B；旧新来自同一实体实例但字段已变化仍能刷新；空↔非空、header、loadMore、追加期间刷新、销毁期间回调均正确；5000条列表 diff 不占主线程。遵循 [DiffUtil 的不可变数据及后台计算要求](https://developer.android.com/reference/androidx/recyclerview/widget/DiffUtil)。

### T03 / P1：封面展示与预取共享请求规格

**改动**：GlideLoader、RecommendPrefetcher.preloadCover、RecommendFeedAdapter；必要时 SmartCoverTransformation。

新增 `CoverRequestSpec(url, widthPx, heightPx, transformVersion)`，展示和预取都走 `CoverRequests.build(RequestManager, spec)`，统一 model 类型（String）、override、变换和磁盘策略。卡片与推荐全屏是不同 spec，不能互用尺寸。尺寸来源布局实测/容器宽高和卡片比例；未完成布局时用 doOnLayout 后加载，预取用相同容器规格，横竖屏变化生成新 spec。不允许 SIZE_ORIGINAL 预取。

将 ImageView URL tag 改为完整 spec + 请求状态；失败允许重试，clear/onViewRecycled 时一并清 tag。记录 spec 后异步方向回调必须校验当前绑定 key，避免复用错位。SmartCoverTransformation 的方向登记是 transform 副作用，resource disk hit 不会重跑 transform：方向未知不能根据处理后的16:9图反推；保留未知语义，必要时使用独立元数据缓存。方向缓存改为容量800的LRU，不能满时整体清空。

Glide 磁盘策略先维持当前等价策略，通过 DataSource 统计命中再决定是否使用 DATA/RESOURCE；不一律扩大容量。变换算法改变时更新缓存 key 版本。缩略模糊图可从 BitmapPool 取还，必须 try/finally 且不回收框架持有的 source。

**验收**：4K竖图/横图、首次布局宽高0、旋转、同URL不同尺寸、404重试、资源磁盘缓存命中场景；预取后展示不重复相同规格解码，峰值 bitmap allocation 降低，主体裁切与视觉效果保持。依据 [Glide 缓存键包含尺寸与变换](https://bumptech.github.io/glide/doc/caching.html)，不能以网络缓存命中代替解码缓存命中。

### T04 / P1：推荐预取窗口、当前页优先与可取消预热

**改动**：RecommendPrefetcher；新增 `PrefetchScheduler`；Fragment 在翻页、隐藏和前后台切换时更新窗口。

**接口**：`resolveNow(candidate, callback)` 保持；新增 `updateWindow(currentKey, nextCandidates, generation)`、`cancelBackground()`；resolveNow 返回订阅句柄，支持独立取消等待者。下载等待者不能被翻页取消误伤。

策略：当前页解析独立1并发，后台解析最多2；后台待队列≤8，只保留最新窗口，当前页可将相同key后台任务提升优先级而非重复解析。foreground/background 同 key 共用一个 single-flight registry，完成在主线程对有效等待者分发。已发起背景请求移出窗口后无前台/下载等待者则 cancel；不能只停止回调而继续耗流量。优先级调度与注册表统一串行访问，避免并发 put/remove 竞态。

warm 同时1个、待队列最多紧邻1条。活动 HttpURLConnection/流需要可关闭句柄；翻页/隐藏/release 立即移除旧任务并断开。保留用户预取开关：关闭时不后台解析/封面预取/字节预热，用户明确请求的播放和下载解析正常执行。

MP4 512KiB 为应用读取上限，read 每次最多 `min(bufferSize, remaining)`；Range 被忽略时达到上限立即关流并记录实际读取量，底层代理仍可能自主取数，必须以网络统计区分，不能宣称全链路绝对只耗512KiB。HLS 当前直接读 manifest 未形成媒体缓存，第一期禁止此无收益 warm，保留必要的详情解析；分片预热留给未来播放器统一缓存任务。

失败缓存区分：确定不可用/解析无结果可保留长TTL；断网/超时/5xx短TTL（初值5秒）；用户显式重试可绕过负缓存一次；403失效只允许一次重新解析，防无限循环。继续使用现有签名到期检查与5分钟安全余量。failedUntil 使用LRU≤120并清除过期项。

**验收**：连续快速滑100页时队列不累计，当前页不排在8个过时任务后；前台+下载同key仅1次解析且均回调；释放后无UI回调、活动连接1秒内关闭（受底层响应取消约束需记录）；弱网与下载并行时起播不退化。每类请求分别统计排队时延/命中/取消/浪费字节。

### T05 / P0：HLS 有界下载、串行状态和真实进度节流

**改动**：HlsDownloader、HlsDownloadService；下载列表只接入必要的 key payload 更新，保留已有 FileDownloader 进度节流。

**工作模型**：协调流程使用独立线程；分片使用3个worker（与当前通常有效并发接近），最多额外排队6项。优先使用3个长活worker从 AtomicInteger 取下一片，避免10,000个Runnable；latch只等待3个worker。异常/取消仍要 finally countDown，不在分片池内部等待它自己。禁止以 CallerRunsPolicy 将网络工作回退到调用主线程；有界队列的资源控制参考 [ThreadPoolExecutor](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)。

**取消与文件**：维护活动连接集合，暂停/取消时 disconnect 并停止领取新片。下载到 `.part`，完成并校验后 rename 为正式片，再写完成清单；续传不能只凭非空文件认为完整。清单带manifest摘要/分片URL摘要，URL签名变化后保守不复用不匹配片，避免同URL哈希/相同片数误复用。`stop(true)` 等workers关闭后才清理任务临时目录，避免边写边删。仅处理当前任务明确归属目录，保留暂停片段。

Service 的 ACTION_START/PAUSE/CANCEL 首先在主线程按现有要求及时 startForeground，随后派发到单线程 HlsTaskCoordinator。DB、MediaStore归档、文件删除和任务切换不在 Service 主线程执行。worker只发布 `SegmentProgress(taskId, done, bytes)`；coordinator 校验taskId后聚合。任务状态 STARTING→DOWNLOADING→MERGING→REMUXING→ARCHIVING→COMPLETED；PAUSED/CANCELLED/ERROR 为终态分支，终态只能提交一次。

节流必须在昂贵操作之前：内存采样随事件更新；普通通知与广播各500ms一次；进度DB写2秒一次，保留最新值；暂停/错误/完成立即flush。每次进度不 findItem；启动时在coordinator查id，后续按id更新本任务进度列，避免持久化过时实体覆盖收藏/来源。进度单调：采用聚合后的累计值，不信任乱序的旧done/bytes。合并完成前100%分片不能标记整个任务completed；只有成品校验和归档处理完成后提交完成态。

先保留 TS合并→MediaMuxer 流程。统计片段总字节、合并、转封装和归档各阶段空间；空间不足（估算片段+merged.ts+mp4+可能归档副本，再加安全余量）时清晰失败且保留可续传片。不能未经验证直接把 TS 文件当 MP4 或删除必要中间文件。

**验收**：10,000片无Runnable线性积压；并发≤3；暂停/取消阻塞连接后1秒内停止新增读取；暂停续传不复用.part；连续两次START、暂停后重启、旧成功回调均不能污染新任务；中途写失败/空间不足不会completed；合并/归档阶段取消不复活；>2GB 字节数正确。100个短片在1秒内结束时，普通通知/广播/DB写仍满足门槛，起止及阶段切换事件单列计数。

### T06 / P0：推荐状态单写者、尾沿保存和原子替换

**改动**：RecoStore、RecoEngine、RecommendFeedFragment.persistAsync/onDestroyView；新增进程级 `RecoPersistenceCoordinator`，持有 appContext，不持有 View。

接口 `requestSave(reason, urgent)`；`flushForTest(): Completable`；业务不直接 subscribe(save) 后加入 View 的 CompositeDisposable。普通请求2秒合并，urgent最多500ms后执行；窗口内请求必须安排尾沿执行，不能直接return后永远没有下一次保存。退出页面只发请求，不阻塞主线程等待，不依赖 onDestroy 必达；交互发生时即标脏并排定保存。进程强杀仍可能丢失未提交窗口，不能承诺绝对持久化。

单线程writer在实际执行时获取最新快照并写盘，避免“先快照后排队”导致旧版本后写。所有写入口（含reset）统一走此writer；重置使用epoch，旧epoch任务不得恢复旧数据。成功清脏仍核对dirtySeq；写失败保留dirty并有限重试（1/2/4秒最多3次，之后等下次触发并记录错误），不忙循环。

使用 `android.util.AtomicFile` startWrite/finishWrite/failWrite/openRead 替换先delete后rename，保留 JSON v2 字段可读，首次读取兼容旧文件。保留写者互斥，AtomicFile 自身不提供线程锁，参见 [官方说明](https://developer.android.com/reference/android/util/AtomicFile)。写错误不能删原文件。directory exists/mkdir 也属于IO，应移出状态锁，不沿用“mkdir纯内存”的旧注释。

画像复合修改/dirtySeq/快照需在同一状态锁保护：ConcurrentHashMap只能保证单操作安全，不能保证整个画像、计数器与版本一致。把反馈写入口包装为短事务 `mutateState(...)`，不能持锁做JSON/IO/网络；打分线程用不可变画像快照，保持原有排序公式。参数+scorer以单个不可变RuntimeConfig发布，不能把两个volatile赋值称作原子组合。

**验收**：500ms内最后一次点赞退出页面仍在尾沿写入；保存中再修改会落最新版本；故意让旧请求延迟不得覆盖新状态；reset与save交错不复活旧画像；磁盘写满、finish失败保留上次有效文件；进程中断写入后能恢复上次有效状态；并发曝光/反馈/保存不丢计数。使用设备测试真实AtomicFile，不能凭JVM android桩返回默认值验证。

### T07 / P1：将同步开库从依赖注入关键路径移出

**改动**：AppDbHelper、MySQLiteOpenHelper、必要DI provider、MyApplication；不整体重写 DaggerApplication。

将构造器改为只保存 helper/context，不调用getWritableDb。新增DbRuntime管理DaoSession与初始化状态：`Completable ensureReady()` 在db初始化执行器只执行一次；`requireReadySession()` 仅供worker使用，未ready或主线程误用时调试构建立刻报错并指出调用者。对外现有同步 DbHelper 接口先保留，调用者必须在IO等待ready；不得把Lazy.get首次开库成本挪到第一次主线程点击。

首次开库、迁移、默认分类种子、旧标记修复形成一个有序ready链。需要分类/来源修正的查询在其完成后运行；避免原有后台种子与首次分类查询竞态。失败为可观察错误页/重试，不能让首页永久等待。T05将Service写入迁移后，再全面审查同步DB入口，包括DownloadPresenter.updateV9MmanItem及Mine/Search相关调用；分别改异步，不能只改构造器后保留主线程懒开库。

Application原有进程gate仍执行；通知渠道要保持Service启动前可用。代理/Cookie初始化保留原顺序，不能异步竞态改变网络语义。只有T00 trace确认超过预算的非必要初始化才延后至首帧；先量化HttpProxyCacheServer等DI构造成本，再决定是否同样Provider化。minSdk28的MultiDex.install是否冗余仅为低优先清理，不作为主要收益。

**验收**：主进程和:filedownloader单独启动均无注入同步开库；新装、13版旧库升级、50,000行库、冷启动下载服务均通过；开库只一次，迁移与读写顺序确定，分类不短暂为空。此任务依赖T05/T06及同步DB调用审查完成后再合入，风险高于纯局部优化。

### T08 / P1：本地列表分页和查询索引

**改动**：DbHelper/AppDbHelper/DataManager/AppDataManager、MySQLiteOpenHelper，以及历史/本地收藏/完成下载对应Presenter和界面。禁止手改@Generated实体DAO代码。

新接口 `Page<VideoRow> loadHistoryAfter(HistoryCursor, limit)`、`loadLocalFavoritesBefore(id, limit)`、`loadFinishedAfter(FinishedCursor, limit)`，limit默认50最大100，返回nextCursor/hasMore。历史与完成下载以 `(date DESC, _id DESC)` 排序，cursor使用最后一行(date,id)，同时间按id消歧；收藏以id DESC。取limit+1判断hasMore。refresh生成新generation、清cursor，查询用捕获的局部参数；旧分页回调不得污染刷新结果。历史原offset API先保留兼容，界面迁移后再移除。

历史谓词示例：`VIEW_HISTORY_DATE IS NOT NULL AND (date < :t OR (date = :t AND _id < :id)) ORDER BY date DESC, _id DESC LIMIT :n`。使用真实生成SQL列名和参数绑定，不能拼接用户文本。完成下载额外保留status=completed AND downloadId!=0条件。

在50,000行fixture上跑EXPLAIN QUERY PLAN，再选择最少索引：候选为历史非空日期+id索引、本地收藏(isLocalFavorite,id)、完成记录(status,finishedDownloadDate,id)的满足条件部分索引。候选不是要求全部建立；downloadId!=0对普通索引不一定有收益。viewKey唯一索引已经存在，不重复增加。

采用独立 `DbPerformanceIndexes.ensure(db)` 幂等 CREATE INDEX IF NOT EXISTS，接入helper的onCreate/onUpgrade之后及onOpen后台开库路径；查sqlite_master确认已有定义匹配。仅加非唯一索引，不改字段/不提高greenDAO schemaVersion触发全表迁移。建立大索引只在dbReady前后台执行并记录成本；选择收益/写放大可接受的索引。开关关闭时停止新分页使用，不自动DROP用户索引。

**验收**：新装/既有schema13库均建索引；行数和关键字段校验不变；相同时间记录、分页间新增/删除、下拉刷新、连续loadMore、失败重试不重复不漏静态记录；动态历史更新时间移动允许刷新后重新排序，不能声称跨变更绝对快照一致。50,000行首批与深分页达标，页面驻留不加载全表，单行下载写入耗时不显著回退。

### T09 / P2：推荐长会话内存有界且保留回看

**前提**：先做T04有界预取与辅助缓存LRU，测量剩余增长。不能直接删除旧列表改变用户回滑能力。此任务只有长跑确认UI列表占主要增长时启动。

新增 `FeedSessionStore`：内存保持当前页附近最多200条，逐批后台将不可变候选DTO写到应用缓存的会话页文件；最多5000条/50MB/24小时，达到上限才淘汰最早历史并在继续回滑边界提供明确提示。该历史仅为推荐会话回看缓存，不替代正式观看历史；不存签名URL与greenDAO关系。

Fragment使用绝对sessionIndex，Adapter维护windowStart；向前回滑接近窗口边缘时异步载入上一批，向后同理。通过当前VideoKey+像素偏移恢复位置，先装数据后notify，不能让当前位置错误播放另一项。挂载/正在播放项不被淘汰；稳定ID基于会话绝对序号分配，淘汰idMap旧条目不产生新旧ID冲突。

resumePositions改LRU≤500（淘汰只影响非当前断点）；downloadLabelStates仅缓存窗口并在下载事件失效；失败缓存≤120、方向LRU≤800。隐藏页面停止ticker/watcher/预取，内存压力时释放非可见媒体资源，不能删除用户成品/收藏/下载断点。所有新session文件清理走明确路径与任务归属验证，不全盘扫删。

**验收**：1000页往返回滑正确、随机回读旧页可见、当前视频不因窗口搬移重启；旋转与下载回调按key落到正确行；缓存被系统删除时可恢复网络解析/显示重试；内存门槛通过且会话磁盘容量有界。此任务单独合入，可关闭feedWindow恢复旧模型，不能混入T01改首屏。

## 8. 暂缓项与后续触发条件

1. **播放器迁移到Media3/统一媒体缓存**：现有多套播放链、全屏、倍速、手势和下载缓存耦合较深。只有T00证明prepared/解码器准备或媒体重复下载主导瓶颈，才另立迁移方案；先做单源MP4/HLS适配验证，再替换。不能把“依赖很老”当作性能收益证据。
2. **Baseline Profile**：关键路径稳定且benchmark链可运行后单独实验；当前AGP/工具兼容性、release dex与实际安装收益必须实测。不为启用profile先整体升级AGP。
3. **推荐打分/词典算法重写**：候选池已限制120，优先级低于IO与队列治理。仅当trace显示分词/打分占单批客户端CPU>20%或p95>30ms，再做`(dictVersion,title)`有界token缓存与批内复用，保持排序同输入同输出。
4. **APK瘦身/移除OCR等依赖**：已有R8/资源收缩与单ABI；先做APK Analyzer归因，删除任何仍用到的功能须另定产品范围。容量收益不能替代运行时指标。
5. **网络客户端池合并**：MyApplication兜底客户端、API、图片和下载的Cookie/代理/头语义不同。仅在连接复用指标证明问题后按用途共享transport，不能直接复用完整业务client导致Header/Cookie串用。
