# 2026-11-28 实机测试：第 12 轮（验证流程会话同步，发版 1.0.149）

用户关键信息：「我网页端每次登录都要输入邮箱验证」——即每次登录后在 `email_verify.php` 填一次邮箱就能看片。

## 1. 站点行为复核（宿主机、全新会话、严格按浏览器顺序）

```
login.php  (captcha 0509)            -> 302 index.php          （登录成功）
GET  email_verify.php                -> 200 表单（email 预填 1441*****）
POST email_verify.php email=1441...  -> 302 index.php          （响应里没有 Set-Cookie）
GET  view_video.php?viewkey=c744...  -> 302 confirm_email.php?cv=1   （仍被挡）
```

- 把 cookie `EMAILVERIFIED` 手工改成 `yes` 再请求播放页：**仍被 302**，说明该开关是服务端判定，客户端改不动。
- 结论：站点把「已验证」绑在**具体会话**上，而浏览器里的那个会话带了我们复现不出来的状态。

## 2. 据此改的代码（1.0.149）

之前只做了「App cookie → WebView」单向注入；验证动作是在 WebView 里完成的，**站点更新后的会话 cookie 回不到 OkHttp**，
所以返回播放页后原生请求仍是旧会话。本轮补上反向同步：

| 改动 | 说明 |
|---|---|
| `EmailVerifyActivity.syncCookiesToApp()` | `onPageFinished` / `onPause` / 返回键时，把 WebView 的 cookie 解析成 okhttp3.Cookie 写回 `SharedPrefsCookiePersistor`，让原生播放器复用同一会话 |
| （已有）掩码自动清空 + 提示 | 站点把邮箱预填成 `1441*****`，直接提交会被判「Please enter your email.」 |
| （已有）返回自动重试 | 从验证页回到播放页自动重新解析 |

单测 87 项全绿、lint 0 error。

## 4. 需要用户配合的最后一步

在 App 里走一遍他在浏览器里做的动作：打开任意「登录可见」视频 → 去验证 → 填完整邮箱 `1441920979@qq.com` → Submit → 返回（会自动重试）。

- 能播 → 说明会话同步生效，主站起播与评论区可以立刻补测；
- 仍不能播 → 请他在浏览器打开同一条视频（测试用 viewkey `c744e8d87734cfe1be60`）确认是否真能播，
  以排除「浏览器里看的是 3 天前老视频（游客本来就能看）」这种情况。
