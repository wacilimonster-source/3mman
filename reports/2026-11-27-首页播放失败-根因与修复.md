# 首页视频播放失败 — 根因与修复（2026-11-27）

## 结论（一句话）

主站播放页解析里有一条「URL 含 `t=` 参数就当成占位地址丢掉」的判断。源站 2026-11 起把
`t=` 作为**签名参数**放进了真实直链（`?st=&e=&t=&k=&f=`），于是**每一条**能播的主站直链
都被判成占位地址丢空，首页点任何视频都只看到「该视频需要源站播放器验证」。
删除该判断后播放恢复。

## 真实站点取证（www.91porn.com，主机网络直连）

| 场景 | 真实页面证据 | 结论 |
|---|---|---|
| 老视频（游客可看） | `<video id="player_one">` 里 `<source>` 被包在 HTML 注释中，真实地址由 `document.write(strencode2("…"))` 写入：`https://la.btc620.com//mp43/1259929.mp4?st=…&e=1795778050&t=ce8e&k=e046c2&f=…` | 直链带 `t=`，携带后 `curl -r 0-1023` 返回 **HTTP 206 / video/mp4**，是真能播的地址 |
| 新视频（3 天内，游客） | 页面没有 `<video>`/`<source>`，只有 `New videos are for logged-in members only … Guests can watch videos older than 3 days.` | 站点策略：新视频只给登录用户，游客无播放器 |
| 直链格式 | `HttpUrl.resolve()` 往返与原串**逐字节一致**，签名不会被改写 | 用 `HttpUrl` 解析相对/绝对地址是安全的 |

复现脚本要点（离线可跑）：把真实页面存成本地 fixture，mock 站点只把 `strencode2` 里的
媒体地址改写成本地 mp4，签名参数形状（`st/e/t/k/f`）保持不变。

## 根因链

1. `ParseV9MmanVideo.parseVideoPlayUrl()` 里 `hasTQueryParam(videoUrl)` 为真 →
   `requiresSitePlayback = true; videoUrl = ""` → `PlayVideoPresenter` 抛
   `play_source_verification_required`（“需要源站播放器验证”）。
2. `RecommendPrefetcher.isReusableMediaUrl()` 复用同一判断，推荐流缓存的直链也全部被判无效。
3. 次生问题：`RulerCookie` 对 `/view_video.php` 剥掉登录态 cookie（`USERNAME`/`DUID`/`level`…），
   登录用户在播放页也是游客身份，正好撞上第 2 条站点策略。工作区已将该类删除、改回
   `PersistentCookieJar`（本次保留）。
4. 站点策略页此前只能落到“解析失败”文案，无法自解。

## 改动

- `parser/ParseV9MmanVideo.java`
  - 删除 `hasTQueryParam` 及丢弃直链的逻辑（`t=` 是签名的一部分）。
  - 新增 `isLoginRequiredPage()`；解析结果带 `requiresLogin` 标记。
  - 保留 `player_one + /vlk.php` 的 `requiresSitePlayback` 模板判断（真实站点仍存在该模板）。
- `data/db/entity/VideoResult.java`：新增 `@Transient requiresLogin`。
- `ui/mman9video/play/PlayVideoPresenter.java`：带登录标记的结果不写库、不播放，转交视图引导登录。
- `ui/mman9video/play/PlayVideoView.java` / `BasePlayVideo.java`：新增 `needLoginForPlayback()`，
  收起播放区、显示“需要登录才能观看”，弹一次「取消 / 去登录」；登录回来沿用
  `RESULT_CODE_FOR_REFRESH_GET_UID` 自动重新解析。弹窗单实例、同页只弹一次。
- `ui/recommend/RecommendPrefetcher.java`：`isReusableMediaUrl(url)` 不再按 `t=` 判占位；
  顺带删掉已成摆设的 `isPorny` 参数与两个无用 import。
- `res/values/strings.xml`：`play_login_required_title` / `play_login_required` / `play_login_action`。

## 验证

- 单测：`testDebugUnitTest` 78 项全绿（新增
  `realSignedMediaUrlKeepsTokenParamAndReachesPlayer`、`guestBlockedPageIsReportedAsLoginRequired`，
  替换掉锁死旧行为的 `hasTQueryParam_*` 与 `signedPlaceholderDoesNotReachPlayer`）。
- `lintDebug`：0 error。
- 模拟器（com.m3man，地址指向本地 mock，页面用真实站点抓取的 HTML）：
  - 修复前：点视频 → 「视频加载失败 / 该视频需要源站播放器验证」，mock 侧无媒体请求。
  - 修复后：同一点击 → mock 收到 `/media/qa.mp4?st=…&e=…&t=ce8e&k=…&f=…` → 正常播放。
  - 游客拦截页 → 「需要登录才能观看 / 该视频仅登录用户可观看；游客只能看 3 天前发布的视频」+「去登录」。

## 仍需注意

- 游客身份下 3 天内的新视频站点本身不放行，App 只能引导登录，不能绕过。
- 工作区本次同时保留了“不再剥登录 cookie”和“请求不再伪造 `X-Forwarded-For`”的改动：
  登录用户据此才能拿到播放器；游客的每日观看次数上限按站点规则如实提示。
