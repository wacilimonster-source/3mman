# 访客限制 / 播放次数限制：实测结论与可落地绕过方案（2026-11-27）

测试目标：`https://www.91porn.com`（App 内「主站」默认地址）与 `https://91porny.com`（App 内「91porny」源）。
测试方式：主机侧 curl（与 App 同款 Chrome UA + Referer + 持久 cookie jar），逐项对照页面是否输出播放器
（`<video>` / `<source>` / `strencode2`）。

---

## 一、结论先说

1. **「游客每天 10 次」这个限制在现行站点上已经不存在**：站点不再下发 `watch_times` cookie，
   连续 24 次取播放页（同一老视频 14 次 + 另外 10 个不同老视频）全部正常出播放器，没有任何次数提示。
   App 里 `resetMman91VideoWatchTime`（无脑删 `watch_times`）对现行站点是**死代码**——工作区已删除，是对的。
2. **真正挡住播放的是账号判定**：3 天内新视频对游客**页面级完全不输出播放器**，中文文案是
   「最新视频仅限登录用户观看，请登录后观看。游客可以观看 3 天前的视频。」，英文是
   `New videos are for logged-in members only … Guests can watch videos older than 3 days.`
3. 这个判定**没有任何 header/cookie/参数层面的绕过口子**（下表 12 组实测全部无效，伪造客户端 IP 直接 403）。
4. **唯一实测可用的「不改账号」路线是换源**：`91porny.com` 对游客直接输出 m3u8
   （`<video data-src="https://cdn2.jiuse3.cloud/s/…/hls/<id>/index.m3u8">`），App 里已有这条源和
   `PornyFallbackResolver`（标题 → 站内搜索 → 相似度匹配 → 取 m3u8），目前只接在**下载**链路，没接播放。

## 二、访客拦截绕过测试矩阵（对「3 天内新视频」`viewkey=e9c96f1e737f89904d5a`）

| 变体 | HTTP | 出播放器 | 命中登录提示 | 说明 |

| B 移动端 UA（Android Chrome） | 200 | ✗ | ✓ | 不做设备区分 |
| C `X-Forwarded-For: <随机公网 IP>` | 200 | ✗ | ✓ | 旧版 App 靠这个刷游客次数，现已无效 |

| E 伪造登录 cookie（`USERNAME/DUID/user_level/level/EMAILVERIFIED`） | 200 | ✗ | ✓ | 会话在服务端校验，伪造无效 |
| F `&viewtype=basic&category=rf&page=2` | 200 | ✗ | ✓ | 无路由差异 |
| G `&c=…&action=comment` | 200 | ✗ | ✓ | 无路由差异 |
| H `view_video_hd.php?viewkey=…` | 200 | ✗ | ✗（无提示） | HD 端点同样不给播放器 |
| I `embed_video.php?viewkey=…` | 404 | ✗ | — | 无嵌入端点 |
| J `vlk.php?viewkey=…`（GET） | 200 | ✗ | — | 只回 2 字节，需 POST 参数，仅用于「站点播放器交互」模板 |
| K 去掉 `www` 的裸域 | 200 | ✗ | ✓ | 同一后端 |
| L 随机 XFF + gzip | — | — | — | 响应为压缩体，仅验证传输，不代表策略 |

页面脚本侧：全站 AJAX 只有评分接口（`ajax/myajaxphp.php`、`ajax/myphpajax.php`）与验证码
（`captcha.php`/`captcha2.php`），**没有回传视频地址的接口**；拦截页正文里也没有 `.mp4` 字符串。
→ 结论：拿不到播放器 = 拿不到签名直链，除了登录没有页面级口子。

## 三、次数限制测试

| 测试 | 结果 |
|---|---|
| cookie jar 内容（首页 + 播放页若干次） | 只有 `ga`、`CLIPSHARE`，**没有 `watch_times`** |
| 同一老视频连续 14 次 | 14/14 出 `<video>`+`<source>`，无次数提示 |
| 10 个不同老视频各 1 次（几分钟内，同一 IP） | 10/10 出播放器 |
| 页面文案检索 | 无「每天只可观看」「次数上限」类文案（中英双语都取过） |

→ 「登录用户不受次数限制」这件事在当前站点**没有需要绕过的对象**；反倒是旧代码里的重置逻辑
把「游客身份」当成前提（删 cookie），而这正是把登录态也一起丢掉的历史包袱之一（`RulerCookie` 已删）。

## 四、可落地的三条路线（按性价比排序）

### 路线 A（推荐，已实测可用）：主站被拦 → 同名搜索 91porny 备用源
- 证据：`91porny.com/search?keywords=newlywed+teacher` 返回 3 个 key；`/video/view/<key>` 对游客
  直接给 `data-src=…/index.m3u8`（HTTP 200，85 KB 页面，含 `<video>`）。
- 复用：`utils/PornyFallbackResolver.resolve(dm, title)` 已经实现
  「标题清洗 → `searchPornyVideos` → 相似度 ≥ 0.5 → `loadPornyVideoUrl` → m3u8」，
  现在只被 `DownloadPresenter`/`DownloadEnqueuer` 用于下载。
- 接法（建议做成**用户点一下**，不要自动，避免同名不同片）：
  1. `PlayVideoView` 再加一个回调或复用 `needLoginForPlayback` 的第三个按钮「用备用源播放」；
  2. `BasePlayVideo` 在 IO 线程跑 `PornyFallbackResolver.resolve(...)`（`PornyFallbackResolver` 里有
     `MIN_SIMILARITY=0.5` 与 `searchKeyword()` 清洗，直接用）；
  3. 命中后用**porny 的 item**（viewKey/title/cover 来自搜索结果）重新进入播放页，
     这样收藏/作者/评论都会自然路由到 porny 源，不用改 `PlayVideoPresenter` 的分支；
  4. 标题上标注「备用源：91porny」，并可记一条 `AppLog.i` 便于回溯误配。
- 风险：同名不同片（阈值 0.5 偏宽，建议对结果展示标题让用户确认）；porny m3u8 约 3 分钟时效
  （`RecommendPrefetcher.isSecureUrlExpired` 已覆盖 `?t=&m=` 形状）。

### 路线 B：账号池 + cookie 轮换（对「新视频」有效，对次数无意义）
- 站点注册要验证码（`captcha.php`、`captcha2.php`），所以账号来源只能人工或半自动；
  App 侧要能保存多份 `PersistentCookieJar` 快照并按账号切换（现在只有一个 cookie jar）。
- 判定逻辑：`V9MmanApi.getVideoPlayPage` 返回拦截页 → 切下一个账号重试 → 全部失败再提示登录。
- 代价：多账号维护、风控（同 IP 多账号登录容易触发）、写库要带账号维度（收藏/历史目前按单账号）。
- 结论：技术上可行，工程与合规成本都高，收益仅是「不用游客身份」，不如直接让用户登一个号。

### 路线 C（产品化规避）：游客只给看得到的
- 列表页已解析出「添加时间」（`ParseV9MmanVideo` 的 `info/添加时间`），可对游客把 3 天内新视频
  置灰或移到「需登录」分组，或直接过滤；点开时给登录引导（本次已实现登录引导弹窗）。
- 不改站点策略、不伪造身份，体验从「点了报错」变成「提前知道要登录」。

## 五、明确无效/不建议的方向

- 伪造 `X-Forwarded-For` / `X-Real-IP` / `CF-Connecting-IP`：前者对拦截页无效，后者直接 403。
- 伪造登录 cookie：会话服务端校验，无效。
- 抓站点 AJAX/接口拿直链：站点不提供这类接口；拦截页正文没有任何 `.mp4`。
- 拆 `vlk.php`（站点播放器交互模板）：那是「需要站点播放器交互」的模板分支，拦截页并不触发它。
- 反向删 `watch_times` 之类的「次数重置」：现行站点没有这个计数器，属于历史死代码。
